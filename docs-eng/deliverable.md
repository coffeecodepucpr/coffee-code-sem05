## // What you should have in hand now

If you followed the modules in order, your `api-grupos` folder should contain: `main.py`, `dados.py`, `schemas.py`, `requirements.txt` and a `README.md`. The API should run locally with `fastapi dev main.py`, and the documentation should open at `/docs`.

## // Deliverable checklist

### > Environment and running

- [ ] The project has a virtual environment, and `.venv` is not in the repository (if you use Git).
- [ ] `requirements.txt` pins FastAPI's version range (`fastapi[standard]>=0.143,<0.144`).
- [ ] The API starts with `fastapi dev main.py`, without any error in the terminal.
- [ ] The `README.md` explains how to install (`pip install -r requirements.txt`) and how to run.

### > Routes and methods

- [ ] The 8 routes exist: `GET`, `POST`, `PUT`, `PATCH` and `DELETE` for groups, and `GET` for the subjects list and for one subject.
- [ ] Each route uses the HTTP method that fits the action.
- [ ] The routes use plural nouns and the identifier in the path (`/grupos/{grupo_id}`).

### > Status codes

- [ ] `POST /grupos` returns `201` and the `Location` header.
- [ ] `DELETE /grupos/{grupo_id}` returns `204`, with no body.
- [ ] A nonexistent group returns `404` with a clear message.
- [ ] A repeated name in the same subject returns `409`.
- [ ] Invalid data and a nonexistent subject return `422`.
- [ ] No route returns `200` with an error message in the body.

### > Validation and rules

- [ ] The Pydantic models validate the name (3 to 60 characters), the subject and the limit (2 to 50).
- [ ] `PUT` replaces the whole group and `PATCH` changes only the fields sent.
- [ ] `PATCH` with `null` in `nome_grupo`, `materia_id` or `max_participantes` returns `422`, and does not corrupt the group.
- [ ] The identifier and the creation date are generated by the API, not accepted from the client.

### > Documentation

- [ ] The application has a `title`, `description` and `version`.
- [ ] Every route has a `summary`, and the ones that can fail declare their `responses`.
- [ ] `/docs` opens, and every route works through **Try it out**.

### > Experienced track (optional)

- [ ] The API is split into packages, with one `APIRouter` per resource.
- [ ] The business rules **do not import** FastAPI (Clean Architecture), and a test checks it.
- [ ] Domain errors are translated in **a single place**, with a single error format.
- [ ] (Bonus) The test suite passes with `pytest -q`.
- [ ] (Bonus) The listing has filters, sorting, pagination and the `X-Total-Count` header.

## // What is NOT expected this week

- No database is expected: the data stays in memory and goes back to its initial state when the server restarts.
- No login, permissions or any access control is expected.
- Publishing the API on the internet is not expected. Always use `fastapi dev`, which only serves your own computer.
- No screen connected to the API is expected.

> **CORRECT LOGIC IS WORTH MORE THAN POLISH**
> An API with few routes that returns the right status code in every situation and rejects invalid data with clear messages is worth more in this evaluation than a feature-packed API that responds `200` to everything. What is being evaluated this week is correct behavior.

## // How to review before submitting

> **THE MOST IMPORTANT TEST THIS WEEK**
> In a new, empty folder, copy only the project files (without `.venv`), create a virtual environment, run `pip install -r requirements.txt` and `fastapi dev main.py`. Then run, in Swagger, the 17 requests from Module 13's test script. If everything matches, your API can be reproduced by anyone.

If any step fails, the error message almost always points to the exact file and line: go back to the corresponding module.

## // Where to ask questions

Coffee & Code's weekly meetings exist for exactly this. "My `PATCH` route returns `422` even with the right body, I already checked the `Content-Type`" is much faster to solve than "my API doesn't work". Always include the status code, the response body and the request you made.
